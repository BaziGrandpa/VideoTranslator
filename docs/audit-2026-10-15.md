# Code and documentation audit: October 15, 2026

## Scope and reading order

This audit covers the current working tree, including existing uncommitted work. It is
not a review of only the last Git commit. Start with [README](../README.md), then
[Current behavior](current-behavior.md); use this document to review unresolved decisions.

Inspected areas: configuration/startup, API and persistence, Tokens/Parts/Cues/Sub-cues,
punctuation and Pass 0–3 prompts/validators, provider fallback, review suggestions,
editing/merging/resume position, rebuild/recovery, preview/render/cancellation, cards,
deletion, tests, and maintained technical documentation. Product/channel editorial
references and the topic-map PDF are not application specifications and were not rewritten.

The audit did not translate or rebuild a real project, change project data, delete projects,
start paid/live model requests, or interrupt a running job. Automated tests used temporary
data and simulated translation providers. Browser interactions were inspected in source;
they were not exercised through automated browser end-to-end tests in this audit.

## Findings and resolution status

A02, A04 and A07 are fixed in the working tree. Pass 2's lack of verbatim preservation checks
was accepted as intentional in A03. Other findings remain limitations or open decisions;
manual Split now uses a Segment-level midpoint and keeps source links.

Priority means proposed review order, not a claim that every issue has occurred in production.
"Confirmed" refers to code behavior; potential failure paths are distinguished below.

### A01 — Audio review scope is narrower than the request (high; requirement decision)

**Evidence:** [audio_effect_boundary_segment_ids](../app/services/subtitle_quality.py)
excludes effects when the preceding speech ends in `.?!`, requires speech on both sides,
and recognizes music/applause names and note symbols only. The existing tests explicitly
expect no warning after completed sentences. The user's requested "effect-adjacent Cues"
can reasonably include those excluded cases.

**Decision:** confirm whether to mark every adjacent speech Segment, including one-sided
intro/outro markers and other effects, or retain the current narrower interrupted-sentence
heuristic. Do not describe the present rule as covering every sound effect.

### A02 — Legacy split API did not preserve the current provenance contract (fixed)

**Resolution:** [Repository.split_segment](../app/repository.py) now divides only the
Segment timeline at its midpoint. The left row retains all English and Chinese text; the
new right row is blank. Both retain the same Part and Cue/Sub-cue links. Both exact Segment
Token ranges are null because a manual time boundary may not follow a Token boundary.
The UI exposes Split beside Merge next. Selected-Part rebuild checks complete source
coverage through the component links, and audio review uses the same links when an exact
range is unavailable. Empty text is rejected by the final render gate.

### A03 — Pass 2 autonomy accepted; Pass 3 review policy remains open

**Decision update:** the user confirmed that Pass 2 may adjust the Chinese rather than
preserve Pass 1 verbatim. Absence of a Pass 2 text-conservation validator is therefore
intentional and is not a defect or a submission blocker. Existing prompt wording asks for
preservation more strictly than this accepted product requirement; it is guidance to the
model, not a hard output invariant. No prompt or runtime behavior was changed in this audit.

**Evidence:** [align_part_cues / split_long_cues](../app/services/subtitle_planner.py) and
[materializers](../app/services/cues.py) check structure, IDs, ranges, and nonempty text.
They do not compare normalized concatenated Pass 2 Chinese against the Pass 1 reference,
or Pass 3-2 pieces against their parent. Pass 3-1 can replace invalid boundaries with
proportional estimates and record `boundary_source=proportional_fallback` without adding
a dedicated review issue.

**Impact:** valid Token coverage does not prove semantic alignment. Permitted Pass 2
rewriting is not itself an error; omissions or misplaced meaning still require human review.
A proportional estimate can pass all mechanical review rules.

**Proposed action:** do not add verbatim conservation checks to Pass 2. Separately decide
whether Pass 3-2 needs conservation checks and whether proportional estimates should be a
review category. Do not add
extra model repair requests to hide validation failures. This audit documents the gap and
does not change the existing call budget or add an eighth suggestion type.

### A04 — Empty subtitles can pass the render gate (fixed)

**Before the fix:** [validate_segments](../app/services/subtitles.py) returned no errors for an
empty list. [approve_and_render](../app/main.py) rejects unfinished Parts only when Parts
exist. A failed project with no Parts/Segments can therefore queue rendering through the
API. [render_project](../app/services/renderer.py) launches FFmpeg and then computes
`max(segment.end_ms ...)` before its cleanup `try` block.

**Impact:** empty input raises after process creation and can leave an unmanaged FFmpeg
process. Normal UI workflow reduces exposure but does not make the API gate correct.

**Resolution:** shared validation now rejects empty Segment lists at both the API and renderer
entry points. Duration is calculated before subprocess creation. The renderer uses `finally`
cleanup for all exceptions after spawning, including progress callbacks and output-write errors:
terminate/wait, kill on timeout, close pipes, and remove this attempt's partial outputs.
Earlier completed MP4/SRT files are preserved. No real empty-project render was started.

**Verification:** tests cover failed/review/completed projects rejecting empty renders without
queueing or changing project state, direct renderer rejection before any subprocess starts,
callback/cancellation-check/SRT failures, forced kill after timeout, failure after MP4 rename,
and preservation of earlier output files. Normal output and cancellation tests still pass.

### A05 — No-speech handling and punctuation validity disagree at Part boundaries (medium)

**Evidence:** [Pipeline.translate](../app/pipeline.py) checks speech across the whole
project. [validate_punctuation_annotations](../app/services/punctuation.py) requires at
least one terminal mark for every eligible Part, while the prompt says not to invent a
sentence ending merely because the Part ends.

**Impact:** a music-only Part inside an otherwise spoken project can still reach the model
and fail validation. A valid short fragment with no sentence ending also conflicts with
the validator. The new whole-project no-subtitle guard fixes the reported all-music case,
not every possible mixed-Part case.

**Proposed action:** define empty-speech Part handling and whether genuinely nonterminal
Parts may return no sentence-ending marks. Keep eligibility, prompt, and validator aligned.

### A06 — Render cancellation and publication have remaining failure windows (medium)

**Evidence:** [render_project](../app/services/renderer.py) checks cancellation while
iterating blocking stdout progress lines, then reads stderr only after stdout completes.
SRT writes, MP4 rename, and database publication are separate operations.

**Impact:** a stalled FFmpeg can delay cancellation indefinitely; sufficiently large stderr
output could fill its pipe while the parent waits for stdout. These are code-derived risks,
not observed hangs in the short tests. A crash or filesystem error can leave scratch/partial
artifacts; SQLite cannot roll back renamed files. A04 now cleans outputs for ordinary caught
renderer failures, but abrupt termination or cleanup errors can still leave files.
Normal cancellation/error tests pass.
Progress can also reach 99% early because it uses subtitle duration rather than video duration.

**Proposed action:** independent cancellation polling, continuous stderr draining, guaranteed
process cleanup, and an explicit interrupted-publication cleanup policy. Use media duration
for progress if it is intended to represent the complete video.

### A07 — Card and subtitle APIs disagree on the cancelling lock (fixed)

**Before the fix:** [card API context](../app/cards/api.py) blocked edits for `render_queued` and
`rendering`; [project_is_rendering](../app/main.py) also blocks `render_cancelling`.
The frontend treats all three as locked.

**Impact:** direct card API requests can edit/delete cards while render cancellation is
pending, although the same action is disabled in the UI. This is an API consistency gap;
no production revision corruption was demonstrated.

**Resolution:** the card API now includes `render_cancelling` in its editing lock.
Parameterized API tests cover all three states: create/update/delete return 409 without
changing cards or their revision; reads remain available, and all three mutations work
again after the project returns to `waiting_review`.

### A08 — Review acknowledgement is not issue dismissal (medium; product decision)

**Evidence:** [list_review_issues](../app/main.py) does not filter by Reviewed status.
Mechanical issues are recomputed; `pass3_invalid_output` is retained from saved flags;
audio rules use original Token ownership. Merge retains the left row's stored flags.

**Impact:** a repaired/accepted subtitle can remain in Review suggestions. Approve all and
render can also mark every row Reviewed while issues remain. This is the current design,
not a new regression proven by this audit. The earlier request not to restamp flags on
manual merges remains respected.

**Decision:** keep a persistent suggestion list, or define an explicit acknowledgement
mechanism. Avoid silently equating `status=reviewed` with dismissal during documentation cleanup.

### A09 — Configuration includes an unused height setting (low; legacy residue)

**Evidence:** `MAX_VIDEO_HEIGHT` populates [Settings.max_video_height](../app/config.py),
but no application consumer reads that field. ProjectCreate/repository default to 1080;
the UI sends the selected height explicitly. Data directory and database overrides are
also independent, which was previously undocumented.

**Proposed action:** remove the unused height setting or wire a consistent default through
API/UI. `.env.example` now marks it as unused so changing it no longer implies an effect.

### A10 — Audit metadata does not uniquely identify a pipeline generation (low)

**Evidence:** [record_event](../app/services/translation_audit.py) uses the generic
`cue-segment-pipeline-v1` label from subtitle quality rules; punctuation separately uses
`punctuation-v2`. Full-run audit directory names mix Part numbers and database Part IDs;
historical files survive rebuilds. Selected rebuilds have a separate run ID.

**Impact:** a version label or directory name alone cannot prove which prompt/code revision
produced a result. This is a diagnosis/reproducibility limitation, not evidence of wrong
database ownership.

**Proposed action:** record a full-run ID and prompt/schema/code fingerprints, and use
consistent Part identifiers. Preserve useful existing artifacts instead of deleting them.

### A11 — Filesystem deletion is only partially recoverable (documented limitation)

**Evidence:** [delete_project](../app/main.py) removes project/output directories before
database deletion completes. It rejects active jobs and validates paths; existing tests
exercise deletion and path protection.

**Impact:** a later filesystem failure can retain the database row after some files were
already removed. Shared caches are intentionally outside project cleanup.

**Decision:** current retry-on-error behavior may be sufficient for a local tool. If atomic
user-visible deletion is required, design a staged/trash cleanup flow rather than promise
that database rollback can restore files.

### A12 — UI locks are broader than backend mutation locks during selected rebuilds (low)

**Evidence:** the [UI](../app/static/app.js) locks subtitle editing when
`pending_rebuild_scope` is set. Segment/style endpoints mostly use
[require_project_not_rendering](../app/main.py), which checks render stages only.
The selected rebuild [commit guard](../app/repository.py) rejects changed revisions.

**Impact:** direct concurrent API edits can cause a selected rebuild to fail publication,
even though the UI prevents those edits. The revision guard protects existing edits.

**Proposed action:** decide whether API clients should receive an immediate 409 during
rebuilds, or document optimistic concurrency as supported behavior. Do not remove the guard.
